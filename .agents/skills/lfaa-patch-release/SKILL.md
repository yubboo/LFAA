# LFAA 补丁与正式发布流程

本技能复用 DeepWrite 的流程拆分思路，但版本、构建、备份和授权以 LFAA 当前仓库规则为准。它不自行提交、推送或发布。

## 判断补丁还是正式版本

1. 先读取根 `AGENTS.md`、`开发规范.md`、`docs/系统总体架构.md`、当前 `docs/PROMPTS.md` 合同和相关包说明；核对当前分支与全部既有工作。
2. 普通源码补丁本身不自动增加项目版本；但每次成功生成新的 Windows Electron 安装包都必须消耗一个唯一修订版本。当前更新日志中的 Electron 包状态为“待构建”时，首次按该版本打包；上次已有安装器后，下次打包入口先将修订号加一、要求录入更新说明，再同步产品元数据和更新清单。构建在生成安装器之前失败时，保留待构建版本以便重试；安装器已生成后，版本即已消耗，后续验收失败也不得复用。
3. 其他正式版本使用用户确认或任务合同指定的 SemVer 目标。项目展示版本只能写成 `LFAA x.y.z`；`docs/updata-log.md` 是唯一项目更新日志，每个新版本追加下一个连续编号 `#N`，含日期、项目版本和本次变化。不得覆盖历史记录、加 `v` 前缀或自造渠道后缀。
4. 按实际打包目标核对相应包的 `package.json`、原生桌面配置、安装包命名和 README。各 package 的工具元数据保持纯 SemVer；只同步本版本实际使用的 Owner，避免全仓机械改号。

## 修改、构建和打包

1. 以任务合同规定的允许文件和验收条件为边界；只修改本次补丁/版本所需内容。不得改写构建门禁、降低断言或把未知能力写成已支持。
2. 运行真实存在且与本次目标直接相关的回归、包构建和仓库 Gate。正式桌面目标按 `.agents/skills/lfaa-desktop-package-test/SKILL.md` 执行；预检入口不存在时明确记录。
3. 构建、平台封装和临时组装产物一律进入仓库根 `dist/` 下对应的 `apps/` 或 `.tmp/` 子目录。只覆盖工具明确管理的目标，不清理整个 `dist/`，不将历史备份嵌入新 ZIP。
4. 版本日志与正式版本候选保持一致。若构建或安装验收失败，不标记发布完成、不上传产物；记录失败证据并保留可审阅的修复状态。
5. 需要源码备份时，调用 `scripts/backup-project.ps1`；它按 `docs/updata-log.md` 读取当前项目版本，产物为 `dist/backups/LFAA <版本>.zip`。该 ZIP 排除整个 `dist/`、`.git`、依赖、运行数据和敏感环境文件，与安装包分开核验。

## 外部发布与 Git 边界

- 本地构建、版本文件修改、打包、源码备份、Git 提交、推送、Tag、GitHub Release、npm publish、商店上传和部署是不同动作。
- 用户明确要求“打包/构建”只授权本地生成和核对产物；不因此推送、建 Tag、创建 Release、运行 `publish:cli` 或上传安装包。
- 只有用户明确要求对应的外部动作时才执行；提交遵循 `.agents/skills/lfaa-git-commit/SKILL.md`，并只包含本次授权差异。
- 不创建或依赖 DeepWrite 的 `update.json`、固定 Git 身份、版本格式、产物目录、发布标签或平台流程。LFAA 的更新日志和版本来源只能按本仓库现行合同执行。

## 发布交付记录

逐项报告正式版本号、改动文件、实际构建命令、直接相关门禁结果、产物路径与核对结果、安装/设备测试覆盖范围、源码备份路径（如有），以及未运行或受阻的步骤。没有完成的外部发布明确写为未发布；不以构建成功代替安装或设备验收。
