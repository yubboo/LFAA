历史合同只描述当时的代码、环境和验证结果。若与当前源码冲突，以当前实现和现行规则为准；不要把“源码存在”或“构建成功”当成能力已装配、可执行或体验已验收。

## 开发与验收流程

1. 核对当前仓库、工作区改动和是否已有同目标的未完成合同。
2. 从源码确认入口、调用链、唯一 Owner、消费者、相关设置及其默认值/持久化、数据和权限边界。
3. 在 `docs/PROMPTS.md` 登记目标、允许范围、禁止改变的行为和可观察验收条件。普通问答及纯错字修正不需要合同。
4. 只改完成目标所需的文件，完成一项可独立验收的界面批次后立即检查。
5. 按目标运行直接相关验证。界面改动需在当前源码服务和 ChatGPT 内置浏览器验收真实路由、交互和响应式视口。
6. 在原合同记录每个文件职责、实际验证、失败项和未测边界；同步改变的权威事实，不复制同一规则到多份文档。

详细修改要求见[开发规范](../../开发规范.md)，包边界见[包职责规范](package-responsibilities.zh.md)。

## 任务合同简表

```markdown
## [编号]-[任务名]-[日期]

### 目标与入口
- 用户问题和预期结果：
- 运行入口/页面：

### Owner 与边界
- 调用链和唯一 Owner：
- 相关设置及数据/权限归属：
- 允许修改 / 必须保持：

### 验收
- 可观察结果：
- 实际验证、失败项及未测范围：
- 变更文件及各自职责：
```

小任务可以删去不适用项，并写明“未涉及”。已完成合同归档时，保留原索引链接和历史状态。
