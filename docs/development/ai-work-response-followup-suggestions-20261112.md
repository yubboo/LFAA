# 小鱼 Agent 回复后的上下文建议

<a id="lfaa-ai-work-response-followup-suggestions-20261112"></a>

## 用户目标与范围

小鱼 Agent 每次成功完成一条回复后，都根据本轮公开回答给出 1–3 条相关的后续问题或下一步开发思路，呈现为可点击建议，交互参照用户附图。设置开关开启时，每条历史回复都保留并展示自己的建议，不限于最新一条。建议必须由当前 Agent 模型结合本轮回答生成，不能从固定模板或关键词规则伪造相关性。点击建议只会把文字作为用户消息提交到当前会话；不会自动执行工具或改变权限。

## 入口、Owner 与配置

- 运行入口：共享 AI Work 聊天 `/work` 及复用 `AiWorkChat` 的业务 App 聊天。
- 展示与点击 Owner：`packages/client/ui-chat`；流式元数据与请求回调：`packages/client/connection`。
- 模型决策 Owner：`packages/core/agent-loop`；会话消息和建议持久化 Owner：`packages/core/session`。
- 设置：沿用设置中心 `aiRuntime.promptSuggestions`。默认值为 `true`，由 Settings Owner 校验、账户持久化并通过共享 Client 设置映射读取；不新增或重置配置。关闭时不要求模型输出建议，也不显示建议卡片。若需要补充请求，则同时读取 `aiRuntime.maxModelRequests` 预算；消息气泡与建议控件沿用共享 Appearance 令牌及减少动态效果映射。
- 权限与数据：通常建议随原模型请求生成。模型漏写时，仅在原 `aiRuntime.maxModelRequests` 及子 Agent 已预留额度仍允许时，使用最终主回复所选的同一账户/Provider/模型补发至多一次无工具请求；计入实际请求数和 Token 用量。建议文本作为公开回复的附属数据保存，不保存隐藏推理或工具原始结果。点击后沿现有 `sendMessage`、Agent Loop 与 Permission Owner 处理，原授权模式及工作范围保持不变。

## 性能、安全与可维护性约束

- 正常由原最终模型响应产生建议。若模型未提供建议元数据，且现有 `aiRuntime.maxModelRequests` 扣除主模型与子 Agent 已用/预留额度后仍有余量，则通过最终主回复所选账户发起至多一次仅生成建议的补充请求；该请求只携带有界的本轮用户问题和公开答复，不提供工具，严格计入原请求预算和实际用量。不为补充建议绕过预算或读取账户凭据。
- 私有流式尾段解析使用固定字节/字符上限；建议数量和单项长度由 Session Owner 校验并限制；不能识别的元数据不会进入公开回复正文。
- 页面不新增订阅、请求、计时器、观察器或动画；每条完成助手回复的建议都保留并显示在各自回复下，容器宽度受父区域约束并允许自然换行。
- 建议是普通文本入口而非 Tool/Skill；未点击时无副作用，点击后也须经过当前 App、会话、模型和权限合同。

## 允许与禁止

- 允许修改 Agent Loop 的最终回复指令和元数据解析、预算内的一次无工具建议补充请求、Session 消息投影与持久化、Connection 的流式事件映射、聊天建议 UI/样式、直接相关回归、`ui-chat`/`agent-loop`/`session` 包说明和本合同。
- 禁止绕过请求预算、向补充请求提供工具、自动运行建议、设置默认值变更、额外审批策略、固定推荐模板、权限或项目范围扩张，以及触碰无关工作树、真实账户偏好和运行数据。

## 验收条件与批次

1. 后端与公开消息批次：设置开启时，每条成功完成的模型回复都应给出 1–3 条有上下文的建议；优先共用最终响应，若缺失则在主模型与子 Agent 预留额度扣除后仍有空间时执行至多一次同账户无工具补充请求。正文、复制内容及后续模型历史不包含协议标记或补充响应；每条建议可随 Session 重载恢复。设置关闭时不要求生成或展示建议；失败、截断或未完成回复不展示建议。预算耗尽或补充请求失败时保留原答复且不伪造建议。合成回归确认补充请求使用同一 Provider、计入原预算/用量、不提供工具，且不进入公开正文或模型历史。
2. UI 批次：每条有建议的完成回复都以可访问按钮显示，不随新回复完成而隐藏上一条回复的建议；键盘及触屏可达；点击后只发送该建议文本到当前会话；运行中、无账户或正在编辑等原有不可发送状态继续禁止提交。桌面和窄分栏/短屏不遮挡、无横向溢出，外观跟随主题和减少动态效果。

## 追加目标：每轮持续给出建议

用户在首轮 admin 实测后明确要求“每次都有建议”。原实现把建议生成设为可选，并只在最新完成回复下显示，因此不能满足该要求。模型提示已强化为每条成功答复必须给出至少一条建议，UI 也已改为保留所有回复建议；真实 admin 验证又发现模型仍可能完全不输出建议标签或正文列表。本轮增加预算内的专用无工具补充请求，只在主回答漏掉建议时使用。用相同 admin 会话连续发送至少三轮通用问题，核对每轮建议持续显示、补充请求实际生成建议且不调用项目工具。

完成前运行直接相关回归、受影响包构建、Client 类型检查、正式 Web 构建及差异检查。每批完成后均在 ChatGPT 内置浏览器验证当前源码服务的实际路由并记录视口、交互和截图。默认不修改账户设置或使用真实 Provider；如用户明确要求真实账户对话验证，按要求执行并记录账户范围、实际交互结果及未测项。未测的真实模型行为和帧时间如实记录。

### 追加缺陷：建议点击后仍可重复提交

用户补充指出：点击某条回复建议并把它作为用户消息发送后，原回复下该建议仍保留；等待新回复完成后还可再次点击，造成同一建议重复提交。截图中被点选的问题仍在旧回复下，且已经作为新用户消息出现在后续位置。

本次修复验收：

- 点击某条建议后，该条立即从原回复下消失；同回复的其他建议仍可用。
- 在 React 完成重绘前连续触发同一建议也只能提交一次；运行中的既有禁用规则继续生效。
- 历史消息重载时，若后续用户消息与该建议文本一致，旧建议仍保持隐藏，避免刷新后复点。
- 单次消费、快速重复提交拦截和历史重载隐藏已由定向代码回归验证；新修改后的 admin/DeepSeek 实页点击验收仍待完成，不能以既往建议功能的对话验收替代。
- 另以无需模型的定向状态回归验证消费和重复提交保护；该回归不替代 admin 真实模型验收。

### 追加缺陷：窄聊天列 Composer 控件挤压

用户截图显示，中等宽度聊天列中的权限/更多按钮标签换行，模型选择过长，导致工具栏变成两行；更窄时发送控件紧贴容器边缘。源码原先只在聊天容器 `380px` 以下启用图标模式，宽度 `380–520px` 仍保留长标签；即使进入图标模式，模型控件仍可占用过多宽度。

修复按实际 `.ai-work-chat` 容器计算，不依赖全局窗口断点：

- 容器宽度 `≤620px` 时，项目/应用与权限/更多操作收为图标；模型名称截断，附件、权限、更多、语音和发送按钮不折行。
- 模型按钮最大宽度随容器收缩；操作栏以 `max-content + minmax(0, 1fr)` 分配左侧入口和右侧发送组。
- 容器宽度 `≤320px` 时，两组操作分成两行，避免发送按钮超出可用区域。
- Appearance 颜色、字号、焦点样式和减少动态效果仍读取已有共享令牌；未新增设置或 CSS 自定义变量。

内置浏览器 `/work` 使用 admin 登录后，在公告遮罩下对真实 Client DOM 作了只读几何检查；未点击公告或修改用户偏好：
