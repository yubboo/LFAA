# LFAA 包职责与应用装配规范

[English guide](package-responsibilities.md) · [开发规范](../../开发规范.md) · [系统总体架构](../系统总体架构.md)

本文件是开发规范的包边界专项细则，适用于全部 `packages/<领域>/<包名>/`、应用入口、Profile 和 Bundle。新增、修复、迁移及审查必须遵循；能力现状仍以当前代码和系统总体架构为准。本规范不表示既有代码已全部完成审计或迁移，也不改变任何运行权限。

## 1. 权威来源与全量覆盖

- 工程规则：根 `AGENTS.md`、`开发规范.md` 及本细则；运行事实：`docs/系统总体架构.md` 与代码；本轮边界：`docs/PROMPTS.md` 当前合同。
- 完整目录与包状态：由原工作区脚本生成的 [包清单](../harness-packages.md) 和 `docs/harness-packages.json`。不得手工复制包计数、增加另一份目录权威或把 `implemented` 当成已装配/已验收。
- 单包合同：该包 `README.md`、公开入口、依赖与运行时登记。目录名仅用于导航；必须沿调用方、实现、存储及执行结果确认 Owner。
- 逐目录专属职责注解由 `scripts/package-responsibilities.mjs` 维护，清单生成器对真实包树核对无遗漏/多余条目；它只补充职责，不决定目录存在或运行状态。每个目录的职责、源入口、静态消费者与组合声明均在生成清单中单独记录，不能只交付包组表。
- 全仓审查须枚举清单中的每个目录，包括占位、工程与测试包，逐项记录结论；普通功能开发只核对受影响包、直接消费者及必要依赖，不要求每次都重审全仓。
- 规则与实现冲突时记录具体差异、影响和迁移范围。用户确认过的架构目标按合同推进；不能把目标写成已实现，也不能默默用历史文档替代当前基线。

## 2. 每个包必须回答的职责合同

新建或改变包职责时，在所属 README 说明以下内容；既有包缺项，在触及该职责的任务内补齐，不进行无关批量改写。

| 项目 | 必须说明 |
|---|---|
| 目的与非职责 | 包解决什么问题；哪些规则、数据及执行明确归其他 Owner |
| 权威归属 | 自己唯一持有的事实、业务规则、配置映射或协议；引用哪些外部 Owner |
| 公共合同 | 导出入口、服务接口、输入输出、错误、状态与兼容要求；调用方不得穿透私有实现 |
| 运行位置 | client/server/daemon 或工程期；实际平台与限制；不同入口的依赖隔离 |
| 依赖与消费者 | 所需服务、内部包、真实调用方、目标 Profile/Bundle 与能力登记 |
| 内容与范围 | 内置 Prompt/Skill/Expert/Tool 的稳定 ID、来源、内容 Owner 和适用上下文；用户内容的持久化 Owner |
| 设置与权限 | 适用设置路径、默认值来源、校验/持久化/客户端映射；账户、App、项目、节点和权限 Owner |
| 数据与副作用 | 存储所有权、事务/原子写入、幂等、防并发覆盖、取消与未知结果处理 |
| 生命周期与预算 | 注册/卸载、连接/流/进程清理、请求并发、缓存和输出上限及其权威配置来源 |
| 验收与状态 | 直接回归/构建、当前消费者及运行证据；占位、源码实现、已装配、已实测分别注明 |

一个包可以有多个协作入口或源文件；不强制“一包一个函数”，不为目录整齐拆出无消费者包。纯内部库可以不注册为用户能力；对用户可用的产品能力必须按现有插件合同登记并接受生命周期管理。

## 3. 分层与依赖硬约束

1. `apps/*` 负责启动、参数、Profile 选择、平台封装和进程收尾。业务 UI、服务、内容正文及业务规则由对应包持有。平台专属 Electron/Tauri 更新、IPC、签名、安装和进程管理可由现有外壳 Owner 持有；跨平台复用有真实需求后再提取，不机械移动所有应用代码。
2. Bundle 选择和组合已有能力；Boot 加载、登记并管理生命周期。两者不能复制业务规则、内容正文、凭据存储或领域执行器。
3. Client 经认证 API/Remote 调用服务，处理展示、交互、缓存及前端状态。浏览器入口不得运行数据库、服务端凭据、Shell 或节点执行逻辑；共享类型或纯函数可以复用，但不把整个 Host 依赖带入前端。
4. Controller 负责传输协议、身份上下文、参数/响应适配和调用领域服务。领域不依赖 Controller、UI、应用入口或 Bundle；数据库规则、任务状态转移、核心/Java 要求等由领域或现有专责 Owner 唯一维护。
5. Agent Loop 协调模型回合、上下文、工具往返、等待/停止及执行证据，不实现各 App 的业务规则。Tool 负责能力描述、参数/风险适配和调用 Owner；领域工具可置于现有领域 `tool-*` 包或现有适配层。不得仅因名字含 `tool` 批量移动代码。
6. 领域服务通过既有 Jobs/节点合同请求执行；Daemon 验证目标并执行真实操作。控制端不能假定远端文件在本机磁盘，Daemon 不替模型决定业务目标。
7. 包间依赖保持无环；通用协议/基础能力不得反向绑定某个 UI/App。真实共享需求用最小公开合同、现有注入机制或调用方组合解决，不为消除依赖新增万能中间层。
8. 跨包只使用已公开且被 TypeScript、开发/生产运行和构建共同支持的入口；当前公开 `包名/src/*` 入口按现有合同使用，不穿透未公开私有路径，不以长相对路径跨越包边界。运行依赖声明在所属 `package.json`，不能依赖偶然提升到根的依赖。
9. 同包多运行时入口分别装配与构建；跨进程通过协议交换可验证数据，不能共享内存对象或因同包而绕过安全边界。构建只写根 `dist/` 的所属子目录。

典型调用链是 Client → Controller → 领域服务 → Jobs/目标节点 → 执行回报；AI 入口是 Agent Loop → Tool → 同一领域服务。链路依实际能力选择，不强制所有只读能力都经过 Jobs 或 Daemon。

## 4. 全部包组的职责约束

下表覆盖当前包清单中的所有一级包组，定义开发归属约束；包含占位组的目标职责，不表示组内每个目录都有可执行能力。单包实际职责必须以第 2 节合同及真实调用链细化。

| 包组 | 职责及边界 |
|---|---|
| `acp` | 外部 Agent 协议互操作；不能另建账户、Session 或权限权威 |
| `api` | Gateway、认证上下文、Controller 与协议适配；调用业务 Owner |
| `attachment` | 附件元数据与读取/处理适配；复用账户、存储和文件访问 Owner |
| `boot` | 启动、加载、插件生命周期及能力安装适配；不占有领域内容 |
| `browser-use` | 浏览器驱动/操作合同与适配；真实驱动、授权和平台能力分别核验 |
| `bundle` | 有序组合补丁；不实现业务、提示词正文或权限策略 |
| `client` | 共享 UI、Connection、模块、状态、主题和布局；不承担后端业务权威 |
| `compaction` | 有界上下文压缩与策略适配；不改写权威会话历史或重放工具 |
| `computer-use` | 桌面观察、输入、应用发现/启动与平台适配；真实结果回报 |
| `context` | 上下文来源/整理合同；不能复制 Session、记忆或领域数据权威 |
| `core` | Agent 扩展、Loop、Session 门面、Tools 协议、Scope、系统消息组合及记忆协调；各专责 Owner 分开 |
| `credentials` | 凭据保护、认证流程及现有授权策略；不以领域副本或 UI 决定代替 |
| `deliverables` | 交付物描述与收集合同；内容仍归创建它的领域/文件 Owner |
| `document` | 文档与写作领域服务、内容、事务和互操作；文件操作复用已有能力 |
| `experimental` | 显式选择的实验能力；未经消费者/平台验证不进入默认必需组合 |
| `extensions` | 扩展协议与贡献接入；复用现有插件生命周期和隔离 |
| `feedback` | 用户反馈合同及适配；关联原任务/会话，不另造执行循环 |
| `fs` | 文件服务合同、目标文件适配与工具；数据归属、路径校验和执行范围仍受原 Owner 控制 |
| `games` | Minecraft、SteamCMD、运行环境各自领域规则；UI/Tool 共用服务 |
| `goal` | 目标状态与控制合同；目标不替代模型决策或 Agent Loop |
| `guard` | 执行保护与策略接入；不能新增脱离 Permission Owner 的审批模式 |
| `hooks` | 生命周期/事件钩子协议；注册可撤销，不能隐式扩权 |
| `host` | WebServer、节点 Host 和运行环境承载；不成为所有业务的收容包 |
| `identity` | 账户身份和隔离边界；会话、设备和业务不能自建假身份 |

| `test-support` | 隔离测试支持；不得进入产品依赖、装配或发布运行树 |

新增包组须先更新本表与架构归属，再创建实现和消费者；保留明确要求的上游占位不意味着必须实现它。禁止用一个组的概括替代逐包审查结果。

## 5. Prompt、Skill、Tool 与内容归属

- 内置领域 Prompt、Skill、专家指引和领域 Tool 描述由对应内容 Owner 维护，使用稳定 ID 和可追踪来源。通用核心指引由核心 Owner 持有；系统消息组合器只负责组合。必须注入的短核心约束与按需读取的领域全文区分，不能把全部正文常驻注入。
- 通用能力目录/加载器负责发现、筛选、读取及撤销；安装适配器负责来源核验、安装与回读。安装器、注册表、Bundle 和 App 不因装配关系成为内置内容 Owner，不复制正文或另建加载系统。
- 当前 `boot/capability-prompt` 是外部提示词安装适配器，`boot/capability-skill` 是项目 Skill 安装适配器，`skill/tool-skill` 提供目录/按需加载；`core/agent` 登记扩展，实际模型循环归 `core/agent-loop`。这些是导航事实，不表示全部内置领域内容已经完成按需加载迁移。
- 用户安装/编辑的内容归现有账户设置、知识库或项目文件 Owner，按真实来源与存储合同分别维护；不能为“统一归属”把用户内容移入源码或把领域正文塞进通用安装包。
- 模型先看到当前上下文可用的简明目录，再按目标读取适用正文。App 是调用/展示上下文，能力共享不等于账户、项目、App 或节点数据共享。范围筛选是执行合同，不得演变成第二套静态应用白名单或禁止已授权通用工具的权限策略。
- 资料、来源脚本、MCP instructions 和外部 Skill 都是不可信输入；读取不等于执行、安装依赖或扩大授权。Tool 必须具有真实参数解析、风险描述、权限接入、执行器及结果，目录存在不等于 Tool 可调用。

## 6. 数据、生命周期与性能

- 身份、凭据、设置、权限、Session、领域数据和节点执行各有权威 Owner。SQLite/JSONL/本机文件按现有合同协作；查询投影和缓存不能成为第二份事实来源。
- 副作用服务负责事务、并发冲突、幂等和真实状态。派发/接受请求不等于完成；结果未知不得当成功，也不得自动重放。取消不能伪称已终止不可撤销的节点动作。
- 所有注册、路由、订阅、计时器、观察器、流、连接和进程都说明卸载/失败撤销路径。重连、切换账户/App、配置变化和禁用后必须对账；旧结果不能覆盖新上下文或跨账户复用。
- 目录摘要与正文分开读取；日志、会话、大结果、缓存及任务列表有界或分页。复用共享请求、映射及注册，避免重复订阅、请求重叠、逐 token/按键磁盘重活；预算读现有配置，不复制超时/限额默认值。
- UI 使用 Settings 共享外观令牌、容器响应式与减少动态效果；新增控制项先接入设置中心。前端禁用或隐藏按钮不能代替服务端授权。

## 7. 审查、迁移与验收

全仓审查逐目录登记：路径/包名、实际入口与消费者、当前职责、正确 Owner、内容/设置/数据/权限、依赖、装配、运行证据、结论和对应问题 ID。每个目录必须为“有证据保留”“确认错位待修复”“占位不可用”“工程/测试专用”或“证据不足待核验”之一；不能将未知标成合格。

问题逐项登记：能力、当前文件与调用链、错位证据、正确 Owner、风险、影响消费者、最小修复范围、验收条件及状态。按安全/数据一致性、执行正确性、重复规则、性能和维护成本排序；没有证据不移动。范围内发现的其他包问题继续处理或明确阻塞，不能只选 Minecraft 示例完成交付。

迁移保持原稳定 ID、公开行为与用户数据；同步调用方、依赖、类型映射、元数据、Bundle、包 README 和架构事实。数据格式变化给出迁移/兼容/回滚方案；临时兼容实现写明替代位置及删除条件，验证迁移后移除旧业务副本。不得擅自整理真实数据或占位目录。

验收同时满足：

1. 唯一业务/数据 Owner 与公开接口可从真实调用链核对，依赖无环，多运行时隔离。
2. 新/改能力有目标消费者及装配入口；模型目录范围正确，可按需读取内容并经真实工具执行，权限、设置及数据隔离生效。
3. 生命周期清理、取消/未知结果、并发与资源预算有直接相关证据，未实现部分准确标示。
