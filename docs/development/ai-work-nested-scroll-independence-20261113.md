# AI Work 工具列表滚动归属（2026-11-13）

<a id="lfaa-ai-work-nested-scroll-independence-20261113"></a>

## 用户目标与边界

- 按用户最新截图：中间会话保留最右侧主滚动条；同组达到 6 条活动后才启用独立纵向列表，1–5 条活动自然展开，不因单条工具的长说明而给整个工具组加滚动条。禁止组内横向滚动。每条工具活动仍按原有交互独立展开/收起；不把整条回复时间线改成滚动区。
- 最右侧主对话滚动条在跟随最新回复时须到达消息区底部，包括流式输出结束时的最后一次消息提交；用户手动上翻或恢复到历史阅读位置时继续尊重其位置。
- 多工具组沿用细强调色滚动条，列表高度上限为 `min(34dvh, 280px)`，内容超宽时裁去横向溢出。长输出/合同仍由各自已有内容框限制。
- 只修滚轮归属：内层列表仍可滚动时，不把它的 `wheel` 事件记为主对话的用户上翻/下翻；内层到边界且允许滚动链时，主对话自然接续。这样生成中的工具列表滚动不会误改“跟随最新回复”状态。
- 运行入口：Web/Desktop 共用 `/work` AI Work。显示 Owner 为 `packages/client/ui-chat` 的 `AiWorkResponse`、`AiWorkChat` 与 `ai-work-chat.css`；中间区域全局滚动条隐藏/恢复由 `packages/client/ui-workspace` 维护。Agent 活动、会话、权限和工具结果继续归现有 Session、Agent Loop 与 Permission Owner。
- 允许修改：`packages/client/ui-chat/src/AiWorkResponse.tsx`（按同组活动数设置滚动门槛）、`AiWorkChat.tsx` 与 `conversation-scroll.ts`（分离内外滚轮归属，并确保已初始化会话的最终流式提交仍可贴底）、`ai-work-chat.css`（仅分离工具组纵向溢出并关闭横向溢出）、直接相关的长期回归、`packages/client/ui-chat/README.md`、本合同与 `docs/PROMPTS.md`。不改变主滚动条和活动行的既有几何、主题与交互。
- 禁止范围：不改变消息/工具活动事实、分组语义、Agent/Session/权限、账户数据或用户设置；不触发真实 Provider/工具动作，不提交、发布或覆盖其他未提交改动。

## 设置、数据与权限

- 不新增或修改设置。沿用 Appearance 的主题/强调色 `--settings-accent`、既有滚动条宽度、位置/尺寸和减少动态效果映射。
- 消息和工具明细继续读取既有 Session/Agent 活动事实；UI 滚动不改执行状态、权限和数据。
- 不新增订阅、计时器或观察器。滚轮处理只检查已知的内层滚动容器，不逐个读取事件祖先的计算样式。

## 验收条件

1. 同组 6 条及以上活动启用受限纵向列表，内容超过上限时可组内滚动；1–5 条活动不启用组级滚动，长输出只滚动其自身内容框。工具列表没有横向滚动条；每条活动仍可单独展开/收起。回复时间线仍随主对话一起滚动。
2. 内层列表可消费滚轮时主对话跟随状态不变；内层触边且允许滚动链时主区接续；被 `overscroll-behavior` 阻断的内层不误改主区状态；没有内层滚动区时保留原行为。
3. 最右侧主消息列表在跟随状态下连同最后一帧流式提交贴到底部；恢复位置距底部不超过 16px 时视作贴底并对齐，超过范围的历史阅读位置不被覆盖；用户明确上翻后位置不被抢回；回到底部提示、锚点导航与其余滚动恢复行为保持原样。工具列表的布局、上限、滚动条位置/尺寸/颜色保持原样。
4. 目标回归、ui-chat/Web 构建、Client 类型检查及 `git diff --check`；结果逐项区分静态、构建和真实页面验收。
5. ChatGPT 内置浏览器在 `/work` 覆盖桌面和相关窄/短视口；找到真实含长工具列表的会话，检查列表滚动、边界滚动链、主区跟随状态与页面溢出，并记录视口、截图证据及未测边界。帧时间/长任务没有实测时明确保留为未测。

## 实施记录

- 最新截图与实页复核后确认三个实际缺陷：工具列表双轴 `overflow:auto` 会产生水平滚动条；主对话 Wheel 过滤器误把回复时间线列入、却漏掉真正的 `.ai-work-chat__tool-group-items`；工具组只按展开详情后的像素高度启用滚动，因此单条工具的长说明也会给整组加滚动条。现在仅同组达到 6 条活动时启用纵向列表，少量活动自然展开；长输出/合同继续在各自内容框内滚动。
- 流式与工具链源码核查：LLM Owner 逐帧把文本 delta 交给 Agent；结构化工具参数片段先在 Provider 适配器内按调用 ID 聚合，完整响应结束并校验后才交给 Pi Agent Loop。执行前由 LFAA Tool Owner 校验合同和参数、Permission Owner 按当前设置授权；真实执行结果以匹配的 `tool_call_id` 写回下一次模型请求，Agent 继续产生下一段文本或工具调用。工具活动用真实 `contentOffset` 插入同一回复时间线，因此每段连续活动各自成组。UI 不应展示未完成参数或提前派发部分 JSON。
