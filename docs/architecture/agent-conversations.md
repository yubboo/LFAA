# 会话形态：单聊 / 群聊 / Agents

- 状态：**待评审，未开工**
- 提出时间：2026-11-22（Asia/Shanghai）
- 负责人已定：三个入口放**左一图标栏**，顺序为 首页（单聊）→ 群聊 → Agents（管理多 agent 配置）。
- 关联方案：[Agent 与模型解耦](agent-model-routing.md)（本文的前置地基）。分工：那份管「agent 怎么绑模型、失败怎么换」，本文管「一个会话里有几个人、谁在什么时候说话」。
- 范围：单聊、群聊、入口与导航、群聊编排协议。**不做**多用户协作（一个工作区仍只有一个用户）、不做群聊内容对外分享。

## 0. 一句话

把「谁决定下一个发言者」做成会话的属性：单聊由用户决定（一条消息一个 agent），群聊由**代理人**决定（一条消息可能触发一串 agent 依次发言）；Agents 页只是配置，不是会话。

## 1. 为什么是三个入口，不是两个

- 单聊与群聊的差别不在皮肤，而在**调度权归属**。单聊里用户就是调度者；群聊里用户只说一句，代理人替他把活分下去。这两套状态机不适合塞进同一个页面按钮。
- Agents 是「配置」，不是「会话」。混进左二的会话列表会让"点一下是打开配置还是发消息"变得含糊，和现有左二「新对话 / 置顶 / 项目 / 最近」的语义冲突。
- 首页保持现状（单聊），是因为它使用频率最高；群聊是新的高频；Agents 是低频配置，放下面符合分层。

## 2. 概念

| 概念 | 定义 |
| --- | --- |
| **bot** | `AgentDefinition.kind = "assistant" \| "worker"` 的标记。同一份配置，单聊、群聊都能用；`assistant` 偏个人助手（默认出现在首页单聊），`worker` 偏干活。**不另建实体** |
| **代理人（host）** | 群聊里代表用户调度的人，默认「小鱼」，可换成任意成员 |
| **规划者（planner）** | 可选。代理人把「出计划」这一步外包给一个专门擅长规划的 agent；它只出计划、不抢话 |
| **成员（member）** | 群成员，按计划发言 |
| **回合（turn）** | 用户发一条消息触发的一整串发言，用 `turnId` 聚合，UI 折叠成一条 |

## 3. 一轮群聊的完整流程

```
用户发消息
  ├─ 有 @ → 发言顺序 = @ 的顺序（跳过代理人调度）
  └─ 无 @ → 代理人出计划（可外包给规划者）
        → 校验计划（成员 / 人数 / 每人必须有任务）
        → 串行发言（各自绑定 → 各自模型）
        → 代理人收口一句话
        → 停，等用户（默认不自动续轮）
```

### 3.1 路由判定

| 情况 | 行为 |
| --- | --- |
| 用户 @ 了一个或多个人 | 按 @ 的先后顺序发言；不再让代理人调度 |
| 用户没 @ | 代理人（默认小鱼）读消息 + 成员名册，产出本轮发言计划 |
| 群里只有 1 个成员 | 直接交给它，等价单聊 |
| 代理人自己不在成员里 | 允许：代理人可以不出声，只做调度 |

### 3.2 发言计划（SpeakingPlan）

代理人（或规划者）必须输出严格 JSON，不接受自然语言：

```json
{
  "speakers": [
    { "agentId": "reviewer", "task": "审查 session 泄漏", "expect": "问题清单" },
    { "agentId": "implementer", "task": "按清单修", "expect": "改动摘要" }
  ],
  "reason": "用户要一个能上线的最小修法"
}
```

硬校验（任一不满足即**整份计划作废**，不静默采用）：

1. `agentId` 必须是本群成员且 `enabled`；
2. 每位 speaker **必须有 `task`**——不给具体任务的人不出场。这条专门防"礼貌性发言/互相吹捧"，是群聊会不会变成废话大会的分水岭；
3. `speakers.length ≤ maxSpeakersPerRound`（默认 3）；
4. 同一 agent 一轮内不重复出场。

计划作废的降级：**只让代理人自己回答**，并在回合首条标注「计划无效（原因），已降级为代理人直接回答」。降级必须可见，不允许假装正常。

### 3.3 规划外包

配了 `plannerAgentId` 时：代理人先把「用户消息 + 成员名册（含每人一句能力描述）+ 预算」交给规划者，拿回计划，再按计划执行。规划者默认不发言；如果它也在 `speakers` 里，按正常成员处理。

这一步对应负责人说的「交给一个专门适合做规划的 agent」。它也是把"规划能力"和"执行能力"分开绑模型的入口——规划用强模型、执行用便宜模型。

### 3.4 串行发言

- 每位成员 = 一次独立的 agent run，`agentId` 决定它的模型绑定（走[模型层](agent-model-routing.md)的 `BoundLlm`）。
- **全员共享同一份会话历史**（负责人已定）：前一位的发言原样进入后一位的上下文，各自只差在系统提示与模型。
- 成员步数上限 `memberMaxSteps`（默认 12，低于单聊，防止一个人把一轮吃光）。
- 群聊内**禁止调用 subagent**（第一版）。否则 3 个成员各自再开子 agent，成本指数级失控。
- 串行也让「审批」天然排队：同一时刻最多一个 agent 在等用户批准。

### 3.5 收口

代理人一条总结（默认开，可关）：本轮谁做了什么、结论是什么、下一步要不要用户决策。它是这一轮的"退出条件"——没有收口，用户只能靠翻聊天记录猜结论。

## 5. 数据与接口

### 5.1 会话记录扩展

```ts
type SessionKind = "single" | "group";

interface GroupConfig {
  agentIds: string[];          // 成员（不含代理人）
  hostAgentId?: string;        // 代理人，缺省 "xiaoyu"
  plannerAgentId?: string;     // 可选：规划外包
  autoRounds: number;          // 默认 1，上限 3
  maxSpeakersPerRound: number; // 默认 3
  memberMaxSteps: number;      // 默认 12
}

interface ChatSessionRecord {
  // …现有字段
  kind?: SessionKind;          // 缺省 "single"，老会话不受影响
  agentId?: string;            // 单聊：跟谁聊；缺省 "xiaoyu"
  group?: GroupConfig;         // 群聊
}
```

### 5.2 消息扩展

```ts
interface ChatMessageRecord {
  // …现有字段
  authorAgentId?: string;      // 谁说的；缺省=用户或会话 agent
  turnId?: string;             // 同一轮群聊聚合
  speakerTask?: string;        // 本轮分给它的任务（UI 显示在气泡头）
  plan?: SpeakingPlan;         // 只记在回合首条，回看"为什么是这几个人说话"
}
```

单聊消息不写这些字段，历史数据与现有渲染完全不变。

### 5.3 接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/api/group/runs` | 起一轮群聊（`sessionId` + `userMessage` + 可选 `mentions[]`） |
| GET | `/api/group/plan/:turnId` | 回看该轮计划与校验结果（调试与透明度） |
| PATCH | `/api/sessions/:id` | 扩展 `kind` / `group`（与模型层共用这条） |

群聊的每位成员内部复用 `AgentService` 的运行入口，不复制一套循环。

### 5.4 SSE：一条流，多个说话人

现有事件流是「一次 run → 一串事件」。群聊是「一个 turn → 多个 run」，因此在外层加四个事件，内部沿用现有事件：

```
turn_started   { turnId, speakers: [{ agentId, task }] }   // 计划生效
speaker_started{ turnId, agentId, step }
  …现有 run 事件（附带 agentId / turnId 字段）…
speaker_finished{ turnId, agentId, status, model, cost }
turn_finished  { turnId, summary, usageByAgent }
```

**兼容约束**：不带 `turnId` 的事件就是今天的单聊行为，前端现有 handler 不需要改；新增字段一律可选。这条要和模型层「agent loop 47 个用例断言不许改」同一级别对待。

### 6.2 新建群

选成员（可多选）+ 选代理人 + 可选规划者 + 预算三件套（发言人数上限 / 每人步数上限 / 自动续轮）。默认值直接可用，不逼用户先配。

### 6.3 单聊

复用现有 workspace，顶部加 bot 切换（下拉），切 bot 只影响下一条消息，不改历史。

## 8. 验收标准

- 单测：路由判定四种情况、计划校验四条规则、降级路径、`turnId` 聚合、SSE 字段兼容（无 turnId 时行为不变）。
- 集成：起 Host，建群（代理人 + 2 成员），用户不 @ 跑一轮，确认计划生效、发言顺序、消息 `authorAgentId` 与 `model` 如实记录、成本分账正确。

- 门禁：`pnpm check` / `lint` / `typecheck` / `test` / `build` / `verify:web` 全过。
- 日志：每阶段 dev-log 一条，G4 交付时 updata-log 一条（群聊是用户可见新功能）。

## 9. 风险与明确不做

| 风险 | 处理 |
| --- | --- |
| SSE 协议变更打穿现有单聊 | 新字段全部可选，无 `turnId` 时零行为变化；前端老 handler 不改断言 |
| 群聊变废话大会 | 计划里每位 speaker 必须有 `task`，否则不出场；收口由代理人强制 |
| 成本失控 | 默认 3 人 × 12 步；单回合显示成本；群内禁止 subagent；`autoRounds` 默认 1 |
| 多人同写一个工作区互相踩 | 串行发言天然只有一个人在跑；工作区租约沿用现有机制。第一版群聊默认**只读模式**，要写必须用户在回合开始前显式放开 |
| 历史膨胀 | 回合折叠 + 收口摘要；不把每个成员的完整步骤塞进后续上下文（只给结论） |
| 代理人调度失败 | 降级为代理人直接回答，且失败可见；不静默、不重试到死 |

明确不做：多用户协作、群聊内容分享/导出、跨群引用、群聊内嵌套子 agent、自动无限续轮。
