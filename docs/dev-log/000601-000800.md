# DEV-000601｜浏览器下载位置跟随系统「下载」目录并可自定义

- 任务编号：DEV-000601
- 英文任务名：browser-downloads-location
- 时间：2026-11-26 15:21–15:45（Asia/Shanghai，UTC+08:00）
- 类型：fix（设置中心「浏览器 → 下载位置」默认值写死）+ feat（跟随系统 / 恢复默认）
- 状态：完成
- 审批级别及批准证据：A1，负责人贴出设置中心截图并在「下载位置」一行画红框，要求「默认下载位置是用户自己电脑里面的 Downloads 位置，不能写死，自动检查用户自己的 Downloads 在哪，然后支持自定义更改下载位置」
- 关联：DEV-000510（浏览器设置体系与下载位置初版）、DEV-000515（双引擎下载闭环）、UPDATE-000601

## 现场事实

- `browser-settings.ts` 的默认值写死为 `join(homedir(), "Downloads")`；本机 `%USERPROFILE%\Downloads` 实际已被重定向到 `D:\Downloads`（`HKCU\Software\Microsoft\Windows\CurrentVersion\Explorer\User Shell Folders` 的 `{374DE290-123F-4565-9164-39C4925E467B}` = `D:\Downloads`），设置页却显示 `C:\Users\Administrator\Downloads`。
- 更隐蔽的一层：`update()` 会把整份归一化配置（含默认下载目录）落盘，任何一次开关改动都会把当次机器的默认路径固化；换机 / 换用户后仍会显示别人的绝对路径，且本机该目录存在时无法靠「不存在就回退」识别出来。
- 「更改…」原生目录选择器本身可用（DEV-000510 已做），缺的是「默认跟随系统」与「恢复默认」。

## 本轮目标与非目标

- 目标：默认下载目录自动取本机系统「下载」目录（Windows 支持重定向到其它盘）；本机默认路径不再写进设置文件；保留自定义选择并提供「恢复默认」。
- 不在范围：下载命名 / 同名并发策略、下载前询问保存位置开关、桌面端 Electron `WebContentsView` 的临时下载暂存目录（`apps/desktop` 的 mkdtemp，与本设置无关）。

## 调研与参考

- 问题与关键词：Windows Downloads known folder redirection、FOLDERID_Downloads、SHGetKnownFolderPath、Electron `app.getPath('downloads')`、XDG `user-dirs.dirs`。
- 项目内已有实现：
  - `packages/workspace/workspace/src/system-paths.ts` 的 `resolveUserDocumentsDir()` 已用 PowerShell `[Environment]::GetFolderPath('MyDocuments')` 跟随系统「文档」重定向，是同类需求的既有做法；
  - `apps/desktop/src/paths.ts` 用 Electron `app.getPath("documents")` 拼默认工作区，注释明确「用户可能把它重定向到 D 盘，不写死盘符或用户名」；
  - `packages/core/browser/src/downloads/download-file.ts` 的 `publishDownload()` 已负责 mkdir 与同名编号，本轮只改「目录从哪来」。
- 外部来源：
  - Downloads 已知文件夹 GUID `{374DE290-123F-4565-9164-39C4925E467B}` 及其在「User Shell Folders」中的重定向位置：<https://learn.microsoft.com/en-us/answers/questions/3717839/system-folders-downloads-and-desktop-system-folders>（查阅 2026-11-26）。
  - `FOLDERID_Downloads` 常量定义 `{0x374de290, 0x123f, 0x4565, {0x91,0x64,0x39,0xc4,0x92,0x5e,0x46,0x7b}}`：<https://pkg.go.dev/github.com/winlabs/gowin32/wrappers#FOLDERID_Downloads>（查阅 2026-11-26）。
  - Electron `app.getPath('downloads')`（等价 `SHGetKnownFolderPath(FOLDERID_Downloads)`）：<https://www.electronjs.org/docs/latest/api/app#appgetpathname>（查阅 2026-11-26）。
  - XDG `user-dirs.dirs` 的 `XDG_DOWNLOAD_DIR` 语义：<https://manpages.debian.org/unstable/xdg-user-dirs/user-dirs.dirs.5.en.html>（查阅 2026-11-26）、<https://wiki.archlinux.org/title/XDG_user_directories>（查阅 2026-11-26）。
- 候选方案与取舍：
  - A. 继续 `homedir()/Downloads`：零成本，但本机就被重定向打脸，且设置文件仍会固化路径，否。
  - B. 只走 PowerShell `Shell.Application.Namespace('shell:Downloads')`：语义最准、中文用户名安全，但每次约 300–600ms，且依赖 PowerShell。
  - C. `reg.exe query` 读 `User Shell Folders` 快速路径 + PowerShell 兜底 + `homedir()/Downloads` 末位回退（采用）：常态约 30ms；注册表值缺失或中文路径被控制台代码页打坏（出现 U+FFFD）时自动降级。
  - D. 引入 npm 包（如 `windows-known-folders`）：为一次路径解析新增依赖，多数包同样绑定 `SHGetKnownFolderPath`，维护面更大，否。
- 结论：改造适配 + 自研小型解析器（C）。仓库已有「跟随系统目录」的做法可以照方向做，但没有可复用的跨包工具，浏览器包也不应反向依赖 workspace 包。
- 许可、维护与安全：无新增依赖；只用系统自带的 `reg.exe` / `powershell.exe` 只读查询，4–8 秒超时，失败静默回退。
- 未采用项及原因：B 作为唯一路径太慢；D 引入依赖无收益。

## 调整

- 新增 `packages/core/browser/src/settings/system-downloads.ts`：
  - `getSystemDownloadsDir()` 进程内缓存一次；Windows 先 `reg.exe query` 读 `User Shell Folders`，展开 `%USERPROFILE%` 一类变量；结果不存在或含替换字符时走 PowerShell `shell:Downloads` 兜底；再退 `homedir()/Downloads`；
  - Linux 支持 `XDG_DOWNLOAD_DIR` 与 `~/.config/user-dirs.dirs`；macOS 退 `~/Downloads`；
  - `resetSystemDownloadsCache()` 供测试丢弃缓存。
- `browser-settings.ts`：
  - `DEFAULT_SETTINGS.downloadDir` 改为 `""`（空串 = 跟随系统）；
  - `normalizeConfig` 区分「未提供」与「显式空串」，后者表示恢复默认；
  - 新增 `resolveDownloadDir()`：空串 / 非绝对路径 / 等于本机系统目录 / 等于旧默认 `homedir()/Downloads` / 其他机器遗留且本机不存在的 `<用户>/Downloads` → 系统目录；其余原样保留为自定义；
  - `update()` 只落盘「空串或自定义绝对路径」，本机默认路径不写盘；`get()` 与 `readForDownload()` 返回解析后的真实路径；新增 `getDownloadDirSource()`。
- `http-handler.ts`：`GET/PUT /api/browser/config` 一并返回只读的 `downloadDirSource`（不参与落盘），供设置页决定是否显示「恢复默认」。
- 客户端：`browser-client.ts` 透出 `downloadDirSource`；`BrowserSettingsView` 拆出 `Browser-Downloads-Group.tsx`（原文件加到 418 行触顶 400 硬上限），下载分组显示路径 +「系统默认」标记，自定义时多出「恢复默认」，选择失败仍走设置页 notice。

## 风险、回滚与遗留

- 取舍：旧默认路径（`homedir()/Downloads` 与不存在的 `<用户>/Downloads`）一律视为「跟随系统」。若用户系统下载目录在 D 盘、却偏要手动选回 `C:\Users\<自己>\Downloads`，会被折叠成跟随系统；这类用户可改选其它目录。优先保证换机后不写死别人的路径。
- 自定义目录若不存在且不是 `<用户>/Downloads` 形状会原样保留，下载时由 `publishDownload()` mkdir（保持原行为）。
- 探测结果在宿主进程内缓存一次；运行期若在 Windows 里改了「下载」位置，需要重启宿主（桌面端重启应用）才生效。
- Linux 桌面依赖 `~/.config/user-dirs.dirs`，缺失时回退 `~/Downloads`；未在 macOS 上实机跑过（代码走 `~/Downloads` 分支）。
- 回滚：删除 `system-downloads.ts`，把 `DEFAULT_SETTINGS.downloadDir` 改回 `join(homedir(), "Downloads")`，撤销 `resolveDownloadDir()` 与 `downloadDirSource` 相关代码即可；设置文件里空串会被旧代码当成「空值」回退旧默认。
- Git：未提交、未推送。

# DEV-000606｜会话区贴底不再抢用户滚轮（修「来回跳、滚动不下去」）

- 任务编号：DEV-000606
- 英文任务名：chat-scroll-ownership
- 时间：2026-11-26 16:09–16:40（Asia/Shanghai，UTC+08:00）
- 类型：fix（会话滚动所有权）
- 状态：完成
- 审批级别及批准证据：A0。负责人反馈「会话区一直触发上下滚动，来回跳，滚动不下去，一直卡上下上下」，并要求查清是什么 bug。
- 关联：DEV-000561（布局变化按停留位置复原）、DEV-000562（滚动记忆持久化）、DEV-000525（贴底半像素判定）、DEV-000527（晚到内容平滑让位）、UPDATE-000606

## 现场事实

- 复现对象：本机 5173 的真实会话「我们这个项目有什么问题」（`2dc560c6-0b6b-48db-8135-4c61d973c8ba`，单条助手消息高 **20683px**，90 步工具）。
- 无头 Edge（1440×900，playwright-core）在线程尾部注入模拟流式内容（每 60ms 长高 30px），再发真实滚轮上滚 4×400px：
  - 修复前：`scrollTop` 20207 → **21814**，即用户往上滚的同时视口净向下走了 **691px**，距底始终 0–30px；上滚等于没发生。
  - 把增长节奏放慢到 500ms / 1500ms（慢于代码里的 120ms 窗口）后，同样的 4×400px **完整生效 −1600px**。→ 分水岭是「内容增长速度 vs 程序化滚动时间窗口」，不是滚轮、也不是浏览器。
- 代码链路（`packages/client/ui-chat/client/conversation/useChatScroll.ts`）：
  - `pinToBottomSync()` 每次写 `scrollTop` 前把 `programmaticUntilRef` 置为 `now + 120ms`；
  - 流式期间 ResizeObserver 每帧贴底 → 这 120ms 被一直续期；
  - `trackScroll()` 开头 `if (performance.now() < programmaticUntilRef.current) return;` → **用户的滚轮事件被逐条当成程序滚动吞掉**，`followBottom` 永远保持 true，下一帧继续贴底；
  - `!grew` 分支还会把 `userScrollTop` 写回（与上滚前后的实际位置不一致），与贴底写入交替；逐帧采样到距底 10–59px 的摆动，就是肉眼看到的「上下上下」。
- 结论：**贴底跟随没有「用户意图」概念，只靠时间窗口猜 scroll 来源**。流式越快窗口越不会过期，滚动条于是被程序长期霸占。

## 调研与参考

- 问题与关键词：chat auto-scroll fighting user wheel、stick to bottom streaming、programmatic scroll attribution、use-stick-to-bottom、overflow-anchor。

  - `useBoundedScroll.ts`（思考正文 / 浏览器步骤列表）已经用「滚轮 `deltaY < 0` 立刻 `follow = false`」的手势判定，且 `pinToBottomSync` 只在自己跟随时写；

  - `use-stick-to-bottom`（AI 聊天专用贴底 hook）的实现思路：ResizeObserver + 内容变化时保持视觉位置，不依赖 `overflow-anchor`：<https://github.com/stackblitz-labs/use-stick-to-bottom>。

  - `::-webkit-scrollbar` 自定义滚动条仍是元素盒的一部分，会被更上层的元素遮住命中：<https://developer.mozilla.org/en-US/docs/Web/CSS/::-webkit-scrollbar>。

- 根因：`ResizeObserver` 里「内容长高且仍在跟底」只有一条平滑分支（原为 `gap > 28` 就走 `scrollTo({ behavior: "smooth" })`）。刷新时真正的历史是一次性涌入，`gap` 从 268 直接跳到 19959，被当成「晚到的一小块内容」，于是发起跨越两万像素的平滑滚动。
- 该分支本来只为「回合结束后迟到的追问建议 / 改动卡片」（一两百像素）服务，判定口径缺少「涌入体量」这一维。

## 调研与参考

- 问题与关键词：chat reload auto scroll animation、scroll to bottom smooth on mount、late content smooth reveal、scroll jump on refresh。
- 项目内已有实现：DEV-000527 定的三档判定（流式硬贴底 / ≤28px 不动 / 整块内容平滑让位）与 `verify-hover-scroll.mts` 的「晚到 150px 内容单帧 ≤32px」门禁；两者都只覆盖小增量。
- 外部来源（查阅 2026-11-26）：
  - `use-stick-to-bottom` 的说明：内容变化时保持视觉位置，动画只用于「贴住底部」，不做跨屏滚动：<https://github.com/stackblitz-labs/use-stick-to-bottom>。
  - MDN `scrollTo` 的 `behavior: "smooth"` 是按 UA 定义的缓动，跨屏距离会明显拖长（本项目实测两万像素约 1.8s）：<https://developer.mozilla.org/en-US/docs/Web/API/Element/scrollTo>。
- 候选方案与取舍：
  - A. 首次挂载禁用动画（用「会话已就绪」标志）：需要额外感知「历史加载完成」，而 `loaded` 与消息挂载不在同一帧，判不准，否。
  - B. 用「涌入体量」判定：`gap` 超过半屏视为一次性挂载，同步贴底；半屏以内才平滑（采用）。无新状态、可纯函数化、与既有小增量门禁兼容。
  - C. 完全去掉平滑（一律硬贴底）：会推翻 DEV-000527 的观感决定，并让 `verify-hover-scroll` 的 32px 门禁失败，否。
- 结论：B。新增纯函数 `shouldSmoothReveal(gap, viewportHeight)`，`ResizeObserver` 与 `/ 2` 的视口高度参与判定。
- 许可、维护与安全：无新依赖、无外部代码。

# DEV-000615｜刷新/切回会话按记忆位置复原（修「滚到哪都被冲到底或顶」）

- 任务编号：DEV-000615
- 英文任务名：chat-scroll-restore-after-skeleton
- 时间：2026-11-26 17:12–17:38（Asia/Shanghai，UTC+08:00）
- 类型：fix（滚动记忆复原）
- 状态：完成

- 关联：DEV-000562（滚动记忆落盘）、DEV-000561（布局变化复原）、DEV-000606/000611（贴底所有权与刷新动画）、UPDATE-000615

## 现场事实

- 实测（5173，真实长会话，可滚区间 20227px）：
  - 滚到 40%（`top 8091`），存档已是 `{top: 8091, atBottom: false}`；刷新后 **落在 20227（最底部）**，且存档被覆盖成 `atBottom: true`。
  - 另一种时序（骨架期可滚区间为 0）会相反：复原值被夹成 0，`followBottom` 停在 false，刷新后**停在最顶部**——正是负责人看到的「回到最上面」。
- 逐帧追踪（包了 `scrollTop` setter 与 `localStorage.setItem`）：
  1. `t=1118` 复原写入 `min(8091, 268) = 268`（此时只有骨架，可滚区间 268）；
  2. 这次写入触发 scroll 事件，`maxTop - top = 0` 被判成「到底」→ `followBottom` 被翻回 true；
  3. `t=1199` 真实历史挂载，`ResizeObserver` 贴底写入 20227，并在 `t=1553` 把存档覆盖成 `atBottom: true`。
- 根因：**复原发生在骨架容器上**。会话详情是异步的，`useChatScroll` 在 `sessionId` 出现的同一帧就写 `min(记忆位置, 当前可滚终点)`；骨架高度远小于记忆位置，写下去的其实是「骨架的底部」，还顺手把跟随状态改成了真。

## 调研与参考

- 问题与关键词：restore scroll position after async content、chat scroll memory、skeleton height clamp、pagehide flush scroll position。
- 项目内已有实现：`lfaa:chat-scroll-memory`（DEV-000562 的按会话存档，含 `top` / `atBottom`）；`rememberScrollPosition` 已能按当前坐标落盘；本轮的 `pendingRestore` 复用同一份存档，不改存储格式。
- 外部来源（查阅 2026-11-26）：
  - `use-stick-to-bottom` 的 "ignore programmatic scrolls / keep visual position" 与本次「容器还没成型时不要落位」同源：<https://github.com/stackblitz-labs/use-stick-to-bottom>。
  - MDN `pagehide`（比 `beforeunload` 更可靠，移动端与 bfcache 场景也会触发）：<https://developer.mozilla.org/en-US/docs/Web/API/Window/pagehide_event>。
  - 规范：滚动容器在内容变化后浏览器不会替你保留视觉锚点（`overflow-anchor` 已在本项目关闭）：<https://developer.mozilla.org/en-US/docs/Web/CSS/overflow-anchor>。
- 候选方案与取舍：
  - A. 等 `state.loaded` 后再复原：需要把「消息已挂载」信号传进 hook，而 `loaded` 与首屏挂载不在同一帧，仍有竞态，否。
  - B. 复原值先挂起（pending），容器能装下或高度停止变化时再落位；期间自己写入引发的 scroll 不计入来源判定（采用）。
  - C. 改成按「距底部距离」存：只能救贴底场景，中间位置仍需要绝对坐标，且换排版后更难解释，否。
- 结论：B。配 `pagehide` 立即落盘，覆盖「滚完立刻 F5」的窗口。
- 许可、维护与安全：无新依赖、无外部代码。

# DEV-000619｜图片主题下输入区不再叠成一大块白

- 任务编号：DEV-000619
- 英文任务名：composer-mask-image-theme
- 时间：2026-11-26 17:33–17:44（Asia/Shanghai，UTC+08:00）

- 状态：完成
- 审批级别及批准证据：A0。负责人截图圈出输入区下方的大块白区并问「这个底部，怎么有这么一大块区域白？」
- 关联：DEV-000608（四栏统一薄纱）、DEV-000612（右栏薄纱对齐）、UPDATE-000619

## 现场事实

- `ChatWorkspace.module.css` 的 `.composerDock::before` 是一条渐变遮挡：`linear-gradient(to bottom, transparent 0, var(--color-shell) 30%)`，用来让往上滚的正文淡出、不从输入卡片里透出来。
- 图片主题下四栏底色是 `--color-column`（`color-mix(--color-shell 62%, transparent)`），而 `--color-shell` 仍是**不透明**的 `#FFFFFF`（浅色）。两者叠加 = `1-(1-0.62)² ≈ 86%` 白，于是输入区变成横跨整栏、约 137px 高（外加 1.4rem 渐隐）的白块——正是截图里红框那块。
- 实测（1440×900，浅色 + `ocean-cliff-sunset`）：
  - `getComputedStyle(dock, "::before").backgroundImage` = `linear-gradient(rgba(0,0,0,0) 0px, rgb(255,255,255) 30%)`；
  - 像素采样：遮挡区 `(247,247,248)`，同一张壁纸在正文区是 `(182,182,182)`；`--color-shell` 计算值 `#FFFFFF`，`--color-column` 计算值 `color-mix(in srgb, #FFFFFF 62%, transparent)`。

## 调研与参考

- 问题与关键词：image theme white slab、半透明薄纱叠加、composer fade mask、color-mix 叠加透明度。
- 项目内已有实现：
  - `tokens.css` 的图片主题段只覆盖 `--color-rail/panel/surface/topbar/column`，`--color-shell` 保持不透明；
  - 输入区遮挡本来就只在「纯色主题」语境下设计（渐变到面板底色），没有考虑图片主题下栏底色已经是半透明。
- 外部来源（查阅 2026-11-26）：
  - MDN `color-mix()`（半透明混色与叠加结果）：<https://developer.mozilla.org/en-US/docs/Web/CSS/color_value/color-mix>；
  - MDN `background-blend`/层叠与 `isolation`（为什么后绘制的半透明层会继续提亮）：<https://developer.mozilla.org/en-US/docs/Web/CSS/isolation>。
- 候选方案与取舍：
  - A. 把遮挡的终点换成 `--color-column`：不再是不透明块，但仍叠在 62% 薄纱之上（≈86%），实测遮挡区只从 247 降到 227，还是一块浅色带，否。
  - B. 图片主题下直接不画遮挡（`background: none`），正文统一由输入卡片自身的 `--color-surface`（0.8）+ backdrop blur 兜住（采用）；纯色主题保持原样。
  - C. 改成渐变模糊（progressive blur）：观感最好，但要额外合成层与模糊半径调参，收益不抵复杂度，暂不采用。
- 结论：B。图片主题下让位给整栏薄纱，纯色主题零变化。

## 现场事实

## 调研与参考

- 问题与关键词：chat layout boxes、composer overlay vs stacked、scroll fade mask inside scroller、max reading width、CSS container query units。
- 项目内已有实现：
  - `ChatAnchorBar` 的容器查询已经假定「窄栏时刻度条占第 3 行、输入区在第 4 行」，所以主栅格本来就该是四行；
  - `ChatWorkspace.hero.module.css` 已经承载空会话引导区样式，建议条只需搬组件不搬样式。
- 外部来源（查阅 2026-11-26）：
  - MDN `cqi` / 容器查询单位（按容器宽度算正文列宽，不写死像素）：<https://developer.mozilla.org/en-US/docs/Web/CSS/CSS_containment/Container_queries>；
  - MDN `position: sticky` 与绝对定位在滚动容器内的差异（为什么把渐隐从 scroller 内挪到盒子底缘）：<https://developer.mozilla.org/en-US/docs/Web/CSS/position>；
  - CSS-Tricks「fading content at the edge of a scroll container」的两种做法（遮罩层 vs mask-image）与其命中/滚动副作用：<https://css-tricks.com/fading-content-at-the-edge-of-a-scroll-container/>。
- 候选方案与取舍：
  - A. 保留叠层，只把遮罩做窄/做透明：图片主题下仍然要么白块要么糊字，且输入区永远压在滚动条上，否。
  - B. 四块盒子各自成行，渐隐做成会话区盒子底缘的一层绝对定位（采用）：正文区不再被任何东西压住，渐隐只影响最后 1.2rem，且比底部内边距矮，滚到底不糊字。
  - C. 用 `mask-image` 给 scroller 做渐隐：观感最好，但会在容器上再叠一层合成，且窄栏下与滚动条槽冲突，暂不采用。
- 结论：B。栅格四行 + 每个盒子一个文件；列宽用容器单位放宽。
