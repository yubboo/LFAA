# LFAA 开发计划与进度

本文档统一记录 LFAA 的开发阶段、当前进度、待开发事项和验收目标，作为项目执行清单。系统组件职责以[系统总体架构](系统总体架构.md)为准，代码和文档要求以根目录[开发规范](../开发规范.md)为准；发布记录写入[更新日志](updata-log.md)。

## 1. 开发方向

产品目标是通用 AI 智能体与 Vibe Coding 工作台。2026-09-30 起以以下七条执行主线安排开发；原 P1–P7 保留为业务历史与具体 App 的验收记录，不再以继续铺开游戏业务作为 Harness 核心优先级。本轮代码、设置及实际验证见 [交付记录](harness-agent-delivery.md)。

产品身份明确为 **LFAA-Harness**：由 LFAA 自己维护 Harness 运行时、配置档与能力组合（Profile/Bundle）和插件生命周期，基础产品能力以 LFAA 第一方插件/能力包装配。桌面主线目标为 Windows/macOS Electron，Linux 和 Android 为后续目标。当前仓库仍以 Tauri 作为根 Windows 桌面默认打包入口、Electron 只有 Windows x64 包装配置；平台路线正在调整，不能把目标平台写作当前已交付。

### LFAA 跨游戏联机服务 App（LFAA-GAME-CONNECTIVITY-APP-01）

只建设一个统一的 Connectivity App。用户指定的完整功能目标包括游戏组网大厅、跨端邀请、节点/虚拟域名/诊断、语音与小队、聊天、共享、远程协作和房间工具；LFAA 自行设计与实现，不复制 MCTier 自有代码或界面。网络引擎方向采用 EasyTier LGPL-3.0 官方核心，不引入 MCTier 自有的非商业代码。

当前代码已登记单一 App ID、客户端入口、Minecraft 跳转、跨游戏 TCP/UDP 目标合同、账户隔离路线 Owner/API 和三条联机路线的独立区域；Minecraft 仅提供实际运行实例目标。已落地第一阶段基础：管理员可提交 EasyTier 固定版本安装请求，由 Connectivity JSON 任务 Owner 持久化，再由认证节点 Daemon 领取并校验官方 Windows x64 运行包；节点回报真实版本能力，App 显示版本与任务状态。该任务队列与 AI Host Shell、SQLite 分离。EasyTier 网络实例启动/卸载/断线恢复和对等状态、LFAA Relay 数据面、已核验的 Provider、房间账号/邀请/实时成员、语音/聊天/共享/远控等仍未完成；当前不报告虚拟 IP 或虚构在线状态。后续优先接 EasyTier 官方结构化管理 RPC 和真实实例生命周期，再按每个协作 Owner 分阶段交付。

完成条件：设置与数据 Owner 盘点、Client/Host 直接构建和账户隔离核验；目标游戏通过 App 适配器真实接入；EasyTier 运行/卸载/断线恢复、真实虚拟 IP/对端状态、Windows 权限与许可证履约均在目标主机验收；房间 Relay、TCP/UDP 路由、认证邀请与端到端玩家连接实测；协作功能逐项完成用户同意、权限、传输、撤销和资源上限验收。未达到全部功能时只报告已完成切片，不标记整体完成。

#### EasyTier 接入方向（依据官方源码与文档，2026-10-06 核对）

- EasyTier 官方源码将 `easytier-core` 作为跨平台网络状态、路由、对端、连通性与实例生命周期 Owner；`easytier` 原生层组合真实 socket、TUN、DNS、操作系统路由、进程和管理入口；`easytier-proto` 提供管理 RPC 类型。LFAA 不重写 NAT 穿透/路由算法，也不把 EasyTier Web Console 当成虚拟网络核心。
- 第一步已交付 Windows x64 官方运行包 v2.6.4 的固定来源/摘要清单、管理员触发下载、ZIP 路径围栏与核心版本核验；当前没有启动 EasyTier 进程，也没有开放虚拟网卡或网络管理按钮。下一步由单一 Connectivity Daemon 能力实现固定结构的实例启动、停止、状态查询和配置更新，优先用官方本地管理 RPC 读取节点、对端、路由与运行状态。配置写入与回读必须遵循 EasyTier 官方格式/API。不得经任意 shell 字符串或解析未经稳定承诺的人类日志驱动功能。若后续评估直接链接 Rust crate，先做跨平台构建、宿主能力、升级替换和 LGPL 履约验证，再决定是否替换独立进程方案。
- App 数据按网络/设备实例保存 EasyTier 网络配置和授权邀请；网络密钥/令牌走现有 Credentials Owner。虚拟 IP、在线节点、直连或中继链路、故障原因只采信真实管理接口与 Daemon 心跳。启停、断线重连、卸载和配置回滚分别有确定状态，不把“配置已保存”显示成“已组网”。Windows 网络设备、路由和权限需求必须在目标系统核实后再呈现授权提示。
- EasyTier 虚拟组网适合要求加入方运行兼容客户端的私有网络；“朋友只填地址、无需安装”的入口必须由另一条真实公网 Relay 数据面提供。MC Java TCP 可以评估按握手主机名分流；其它 TCP 游戏通常使用独立端口；UDP 游戏按实际 UDP 端口映射，不能只靠 DNS 子域名区分房间。两种接入方式共享一个 App，但不共享网络状态或生命周期。
- 后续按切片推进：① Windows 单节点 EasyTier 实例生命周期、结构化 RPC 与真实节点状态；② 跨设备入网、邀请/撤销与连通性诊断；③ Minecraft/饥荒等 App 的真实 TCP/UDP 目标适配器；④ 自有 Relay 的地址分配、认证、心跳与外网实测；⑤ 语音/小队、聊天、文件/屏幕共享、远程协作分别建立独立权限和传输 Owner。每片完成才开放对应操作。
- 官方资料： [EasyTier 核心架构](https://github.com/EasyTier/EasyTier/blob/main/docs/core-architecture.md)、[管理 RPC 定义](https://github.com/EasyTier/EasyTier/blob/main/easytier-proto/proto/api_manage.proto)、[下载组件说明](https://doc.easytier.cn/guide/download.html)、[快速组网](https://doc.easytier.cn/guide/network/fast-networking.html)、[Web 控制台](https://doc.easytier.cn/guide/network/web-console.html)。项目 README 标注 EasyTier 为 LGPL-3.0；发行前须完成许可证文本/归属、可替换或重新链接要求（如适用）、修改记录与第三方声明核对。此处是工程接入建议，不构成法律意见。

### DSH 非界面能力完整复刻与优化路线（LFAA-HARNESS-DSH-CAPABILITY-PARITY-01）

本路线以 DeepSeek Harness `639ed015397290b3745d163aafe02ffee4aa3f84` 的 316 个两级包目录为能力基线；各目录与当前 LFAA 实现/占位状态见[包目录清单](harness-packages.md)。目录存在、能构建或被标记为“实际实现”，均不证明行为与上游等价或已通过真实环境验收。范围包括所有非界面的运行服务、数据模型、工具、模型服务商、协议、主机/守护进程集成、自动化与互操作能力；`client/ui-*` 中的页面、React 前端框架组件、布局、主题/样式和纯展示实现不复制。它们背后的设置、服务、状态、权限、程序接口（API）和操作仍必须由 LFAA 唯一责任归属提供，并通过 LFAA 自有界面、设置中心、命令或智能体工具使用。`util`、运行时诊断和测试基础设施作为工程支撑覆盖各阶段；测试包不得进入产品运行树。实验组能力纳入完整目标，但在 P4 前保持清楚的实验/未接入状态。

**插件化硬原则：LFAA-Harness 万物皆插件。** 除启动、插件装配、生命周期调度和权限隔离所需的最小 Harness 内核外，所有可用能力都必须以 LFAA 第一方插件或能力包登记、装配、启停、升级、回滚和撤销，涵盖基础产品能力、模型与智能体、应用服务、客户端接入、工具和节点执行。宿主只提供插件运行所需的最小机制，不得藏有绕开插件登记的平行业务实现；插件通过各自唯一的业务、数据、设置与执行责任归属工作，继续服从认证、授权和节点边界。纯内部库可以作为插件实现依赖，但不因此把可用能力移出插件体系。所有包都要在逐包映射中标明属于插件能力、最小宿主机制、工程支撑或明确排除项。

**优化及完成标准：** 每个阶段按“能力合同和唯一责任归属 → 设置/数据/权限 → 插件化实现或可验证复用 → 长期回归 → 配置组合/真实运行验收”推进。优先选择最适配 LFAA 的实现，不以复制上游代码行数作为目标；复用代码或依赖前记录版本与许可。性能优化须提供真实工作量、时延和数据规模证据，安全优化不得绕过认证、授权或改变用户设置，可维护性要求唯一事实归属、插件副作用可撤销、错误路径可恢复。每个实现阶段另立 `docs/PROMPTS.md` 任务合同；只有直接相关回归、配置组合、真实模型服务商/守护进程/桌面等适用验收完成后，才更新包状态。P0–P4 全部完成前不得宣称 DSH 非 UI 能力已完整复刻。

**P0 收口情况（2026-10-04）：** 已按 LFAA 需求完成 P0 能力适配、逐包取舍和隔离回归，不按 61 个上游目录逐一重建。Settings、Session/JSONL、权限、节点和业务服务维持各自 Owner；现有 SSE 承载模型流。Typert 双向流、DSH V0–V4 导入转换、通用 Session 投影/耐久缓存、Platform OAuth、Agent 命令目录及 CLI/桌面交互通道没有当前 LFAA 消费者；真实 OS 沙箱与本机/Daemon 子进程提供方按 P2。验证结果与未验边界见 [P0 取舍审计](harness-p0-audit.md) 和 P0 任务合同。

LFAA 面向 SteamCMD 游戏开服、Minecraft 管理、写作和各应用内的 AI Work。开发采用“控制端 + 节点执行端 + 多端界面”的分布式结构：

- `packages/client/` 提供 Web、Tauri、Electron 共用的界面；每个业务应用同时有常规模式和内置 AI Work。
- `packages/api`、`storage`、`core` 等包组成控制端，集中处理用户身份、权限、游戏业务、任务状态、AI Agent 与节点调度。
- `packages/host/daemon` 部署在本机或远程主机，按授权执行安装、进程、文件、终端和资源监控任务。
- SteamCMD、Minecraft 和写作先作为独立业务应用建设；LLM 驱动的主 Agent 根据需要委派子 Agent，并通过受控工具完成操作。
- 当前采用对标 DSH 的 LFAA Harness。全部上游目录及实施状态见 [包目录清单](harness-packages.md)，实际改动与验证见 [迁移交付清单](harness-migration.md)。Profile 选择 Bundle 补丁，Cordis 管理各进程内的服务和插件生命周期。
- 首阶段拆分随 LFAA 发布的可信内置包，覆盖身份/设置/权限、AI、各业务 App、Client UI 和 Daemon Runner；代码直接迁入新包，不在旧目录外包转发适配层。第三方包安装必须等包信任、权限声明、故障回滚与隔离执行合同落实后再开放。

### MCSManager 参考结论

MCSManager 将产品分成 `frontend`、`panel` 和 `daemon` 三个核心部分：前端负责交互，panel 管理用户、节点连接、认证授权和 API，daemon 管理实例进程、容器、文件和实时终端。它还提供游戏服务端的一键部署、多节点管理与细粒度多用户权限。[项目说明](https://github.com/MCSManager/MCSManager) · [简体中文开发指南](https://github.com/MCSManager/MCSManager/blob/master/DEVELOPMENT_ZH.md)

它的开发安装脚本一次准备项目所需依赖和节点侧 PTY、压缩工具；正式安装则提供 Windows 即用包、Linux 安装脚本和 Docker 方案。[开发依赖安装脚本](https://github.com/MCSManager/MCSManager/blob/master/install-dependents.bat) LFAA 采用相同的三层职责思路，并补充写作和应用内 AI Work。SteamCMD、Java、PTY 等主机运行环境属于 LFAA 的运行数据和部署管理范围，不应混进前端 npm 依赖清单。

MCSManager 允许前端为性能直接连接节点。LFAA 首期先通过 server 执行权限检查、任务审计和节点路由；终端或文件传输确需直连时，再单独设计短期凭证、授权范围和审计方式。

## 4. 后续里程碑

### P4：Minecraft 管理 MVP（当前优先）

## 6. 进度维护规则

- 本文档是里程碑、进度和待办的唯一汇总处，不另外复制一份“开发进度”和“待开发清单”。
- 状态统一使用：`待开始`、`进行中`、`已完成`、`阻塞`。没有代码或可检查产物时，不标为已完成。
- 每完成一个事项，更新状态、完成日期和可核对的产物；遇到阻塞时记录具体原因及解除条件。
- 版本发布与正式版本变更仍记录在 `docs/updata-log.md`；普通任务状态变化只更新本文档。
- 每次开发开始前，先对照本文档、最新[系统总体架构](系统总体架构.md)和[开发规范](../开发规范.md)；用户最新确认的架构决策优先，旧文档只作背景参考。
