# LFAA 开发计划与进度

本文档统一记录 LFAA 的开发阶段、当前进度、待开发事项和验收目标，作为项目执行清单。系统组件职责以[系统总体架构](系统总体架构.md)为准，代码和文档要求以根目录[开发规范](../开发规范.md)为准；发布记录写入[更新日志](updata-log.md)。

## 1. 开发方向

产品目标是通用 AI 智能体与 Vibe Coding 工作台。2026-09-30 起以以下六条执行主线安排开发；原 P1–P7 保留为业务历史与具体 App 的验收记录，不再以继续铺开游戏业务作为 Harness 核心优先级。本轮代码、设置及实际验证见 [交付记录](harness-agent-delivery.md)。

| 主线 | 本轮交付 | 后续验收 |
|---|---|---|
| 1 通用任务工作区 | `/tasks`、首页任务入口、独立聊天默认偏好接入 | 项目文件树、差异与成果审阅、任务列表和真实浏览器视觉验收 |
| 2 独立 Agent 执行核心 | Loop 从 API 分离；后台 Run、断线跟随、显式停止、排队/引导输入、工具协议证据与执行预算 | 进程重启后的人工确认恢复、上下文压缩、长任务与性能基准；不得自动重放写操作 |
| 3 项目与验证能力 | 真实项目文件读取/检索/创建/摘要替换/Git 差异；现有 Shell 接入任务目录与 Shell 设置；账户隔离输出面板 | 真实在线 Daemon 的跨应用端到端验收、交互式 PTY、项目回滚与环境管理 |
| 4 Agent 与专家协作 | 独立模型账户、执行循环、工具范围、数量/深度限制、取消传播与持久化证据 | 并行调度、任务依赖、写入冲突处理、独立专家角色配置与聚合用量 |
| 5 Tools/Skills/MCP 与应用接入 | 可撤销可执行插件工具；项目内 Markdown Skill 发现/读取；设置中心配置 HTTP MCP 服务与真实协议调用 | OAuth、stdio、MCP 资源/提示词、插件安装与版本管理、真实浏览器/桌面 MCP 服务及 ChatGPT↔LFAA 双向任务交接 |
| 6 语音、多模态与质量 | 浏览器语音输入/播报开关和能力检测；真实认证完整装配及运行回归 | 麦克风与目标宿主验收、模型 Realtime 语音、多模态文件、原生电脑观察/操作、重连与性能长期评估 |

核心方向为“大模型 → 主 Agent/子 Agent/专家 → Tools、Skills、提示词 → App 服务与节点执行 → 真实结果 → 模型继续决策”。模型自主判断和分派任务；用户配置的 Provider、模型和权限模式为运行依据。源代码按包组织，浏览器、控制端、节点分别运行。完整多子 Agent 协作与专家独立模型配置仍待实施，当前一次只读专家委派的限制不作为目标架构。

LFAA 面向 SteamCMD 游戏开服、Minecraft 管理、写作和各应用内的 AI Work。开发采用“控制端 + 节点执行端 + 多端界面”的分布式结构：

- `packages/client/` 提供 Web、Tauri、Electron 共用的界面；每个业务应用同时有常规模式和内置 AI Work。
- `packages/api`、`storage`、`core` 等包组成控制端，集中处理用户身份、权限、游戏业务、任务状态、AI Agent 与节点调度。
- `packages/host/daemon` 部署在本机或远程主机，按授权执行安装、进程、文件、终端和资源监控任务。
- SteamCMD、Minecraft 和写作先作为独立业务应用建设；LLM 驱动的主 Agent 根据需要委派子 Agent，并通过受控工具完成操作。
- 当前采用对标 DSH 的 LFAA Harness。全部上游目录及实施状态见 [包目录清单](harness-packages.md)，实际改动与验证见 [迁移交付清单](harness-migration.md)。Profile 选择 Bundle 补丁，Cordis 管理各进程内的服务和插件生命周期。
- 首阶段拆分随 LFAA 发布的可信内置包，覆盖身份/设置/权限、AI、各业务 App、Client UI 和 Daemon Runner；代码直接迁入新包，不在旧目录外包转发适配层。第三方包安装必须等包信任、权限声明、故障回滚与隔离执行合同落实后再开放。

### MCSManager 参考结论

MCSManager 将产品分成 `frontend`、`panel` 和 `daemon` 三个核心部分：前端负责交互，panel 管理用户、节点连接、认证授权和 API，daemon 管理实例进程、容器、文件和实时终端。它还提供游戏服务端的一键部署、多节点管理与细粒度多用户权限。[项目说明](https://github.com/MCSManager/MCSManager) · [简体中文开发指南](https://github.com/MCSManager/MCSManager/blob/master/DEVELOPMENT_ZH.md)

它的开发安装脚本一次准备项目所需依赖和节点侧 PTY、压缩工具；正式安装则提供 Windows 即用包、Linux 安装脚本和 Docker 方案。[开发依赖安装脚本](https://github.com/MCSManager/MCSManager/blob/master/install-dependents.bat) LFAA 采用相同的三层职责思路，并补充写作和应用内 AI Work。SteamCMD、Java、PTY 等主机运行环境属于 LFAA 的运行数据和部署管理范围，不应混进前端 npm 依赖清单。

MCSManager 允许前端为性能直接连接节点。LFAA 首期先通过 server 执行权限检查、任务审计和节点路由；终端或文件传输确需直连时，再单独设计短期凭证、授权范围和审计方式。

## 4. 后续里程碑

### P2：分布式节点基础

1. daemon 使用受保护身份向 server 注册节点，汇报操作系统、版本和可用能力。
2. server 接收心跳，展示节点在线、离线和版本状态；Minecraft 活跃任务通过 30 秒租约续期，租约过期时报告结果未确认，不自动重放副作用操作。
3. 定义任务编号、目标节点、输入参数、进度、结果、失败原因、超时和取消语义。
4. daemon 只处理经认证任务队列派发的任务；通用文件管理仍限定数据根目录和实例路径，AI 主机 Shell 则单独受账户三种项目权限模式控制。
5. 在真实本机 daemon 和一台 Linux 远程 daemon 间完成连通与重连演练。

**验收目标：** Web 控制端能登记并监控本机及远程节点；创建的测试任务有完整状态流转和可追踪结果。

### P3：SteamCMD 开服 MVP

1. 建立可扩展的游戏目录和部署参数定义，先接入一款选定的 Steam 游戏。
2. 实现 SteamCMD 工具安装/检测、服务端下载、目录准备、配置编辑和启动参数校验。
3. daemon 执行部署与进程生命周期；server 持久化实例和任务状态。
4. 前端显示下载/安装进度、实时日志、终端、启动/停止状态、资源使用和可视化配置。
5. 加入备份、失败恢复和重复部署保护，再扩充更多游戏目录条目。

**验收目标：** 用户从 Web 界面选定节点和游戏后，能完成安装、启动、查看日志、停止及再次启动；服务端实例数据、配置和日志按约定位置持久化。

### P4：Minecraft 管理 MVP（当前优先）

Minecraft 进入常规模式后显示应用专属菜单，按“监控、管理、环境”分类：监控包含总览和控制节点，管理包含实例和任务，环境包含 Java 环境；选择实例后展开实例概览、服务器配置、控制台日志和世界备份。总览卡片跳转到对应真实管理页，并通过已接入的 Socket.IO 变更通知刷新状态，保留 REST 快照对账。应用菜单与工作台只负责 Minecraft 业务，不改变最左侧全局导航。顶部常规 / AI Work 切换只改变交互方式；AI Work 复用已有模型服务和账户，但当前不注册 Minecraft 执行工具。

当前实现范围为本机 Windows x64 Daemon、Minecraft Java Edition 官方 Vanilla 服务端：从 Mojang 官方版本清单选正式版，按该版元数据匹配 Java；实例创建时可选目标节点已发现且主版本匹配的 Java，外部 Java 保持原位；选择自动管理时优先用已有 LFAA 托管版，缺少时可通过 Adoptium 官方 API 安装并校验 JRE。创建实例前明确同意 Minecraft EULA；实例启动前 Rust Sandbox Host 为该实例创建独立 AppContainer 身份，验证规范路径，为实例目录授权读写并设低完整性标签、仅为实际使用的 Java 安装目录授权读/执行，再通过显式网络能力创建 Java 进程；Job Object 限制进程数和内存，并在 Sandbox Host 关闭时结束进程。缺少或建立沙盒失败时拒绝创建/启动实例任务，不回退到普通进程。启动、停止、配置写入、日志和停服后世界备份仍通过现有真实任务队列执行。控制节点页展示真实 Daemon 心跳和能力，节点能力来自 Sandbox Host 启动探测，实例状态来自 Daemon 心跳；总览卡片通过实时变更通知显示节点、实例和任务状态。主机 CPU、内存和磁盘采集仍未接入，不以静态或估算数据填充面板。

AppContainer 的 Windows 边界参照 Microsoft 的 [AppContainer isolation](https://learn.microsoft.com/en-us/windows/win32/secauthz/appcontainer-isolation)、[AppContainer implementation](https://learn.microsoft.com/en-us/windows/win32/secauthz/implementing-an-appcontainer)、[Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects) 和 [Mandatory Integrity Control](https://learn.microsoft.com/en-us/windows/win32/secauthz/mandatory-integrity-control) 文档。构建验证不能替代目标 Windows 主机对 ACL、低完整性标签、网络绑定、启动、停止和宿主退出清理的验收。

插件/模组、Bedrock、Paper/Spigot/Fabric/Forge、远程多节点、交互式任意命令、主机资源采集和 Agent 自动操作不属于本轮 MVP。后续完成 Minecraft 后，依用户顺序接 P3 SteamCMD，再接 P5 写作。

**验收目标：** 专属菜单正确切换；在线本机节点与正式版目录真实读取；管理员在同意 EULA 后可创建官方 Vanilla 实例、为实例选择已发现的匹配 Java、查看任务和实际输出、启动/安全停止、修改白名单字段及为已停止实例备份世界；每个 Java 服务进程实际以该实例 AppContainer SID 运行，其他实例数据和宿主机凭据不可访问，能力范围内允许服务端网络，进程内存/数量受 Job Object 限制，并在 Sandbox Host 关闭后清理。刷新后状态来自 server/daemon 持久数据。实际 Minecraft 下载和开服验收需在用户 Windows 主机执行；构建检查不能替代该验收。SteamCMD、写作和第三方插件不得因此标记为已隔离。

### P5：写作应用

写作数据独立于游戏实例，并按账户保存在控制端 SQLite。当前实现作品、作品大纲、卷与章节管理；大纲与正文都在中央编辑器中自动保存，各自保留最近 50 个修订快照。v28 为既有作品无损创建“第一卷”，v29 为既有作品增加空大纲及大纲修订表，v30 增加 AI Host 命令队列。AI Work 同时读取当前作品大纲与选中章节作为受提示约束的上下文，不把正文复制进聊天历史；Agent 按自然语言目标调用对应的大纲或正文工具，支持追加、开头写入、唯一锚点插入及明确要求时整体替换。写作工具仍绑定具体账户作品/章节；在完全权限模式下，AI Host 可按主机权限操作工作目录中的任意路径。资料库、导入导出、图片附件与丰富格式仍待后续设计接入。

**验收目标：** 用户能创建作品、编辑章节、关闭并重新打开应用后恢复内容。

### P6：各应用内的 AI Work

当前已完成 `LFAA-AI-RUNTIME-01` 的 Provider 对话、持久化会话、扩展契约与设置中心分类，并完成 Agent Loop、流式工具调用回传、运行活动持久化、可配置独立模型与工具执行的子 Agent 委派及首批业务工具。`LFAA-AI-PERMISSIONS-01` 的账户模式、单次审批和记忆授权继续由 server 执行；Minecraft、SteamCMD 和受限文件写操作额外强制逐项确认。

1. 在 server 配置 LLM 提供方、密钥、模型、超时和用量；前端不保存模型密钥。
2. 每个应用内提供独立上下文的 AI Work 面板，不增加一个替代业务 App 的全局 AI 应用。
3. Agent Loop 已支持最多 12 次模型请求、最多 24 次工具调用和停止信号；真实 Provider 与工具协议兼容性待实机验收。
4. SteamCMD、Minecraft 与写作专家可由主 Agent 逐次委派只读分析子 Agent；每轮最多一个，子 Agent 不拥有业务工具且不递归。
5. Tools 调用 server 业务服务或 Daemon 任务队列；请求审批对每次写入/高风险操作/主机命令逐项确认，替我审批只对已明确记住且精确匹配的范围免逐项审批，完全权限对当前应用全部已登记项目工具（含任意 Shell 命令和工作目录）免逐项审批。写作工具仍检查账户作品归属；主机命令由在线 Daemon 以自身 OS 账户运行，不在 server 直接执行。Minecraft EULA 同意仍由用户明确完成。Steam 游戏 Runner 和写作作品文件工具未接入。写作 Agent 可调用大纲/当前章节写作 Tool，目标和参数由模型按自然语言指令判断，Tool 对账户作品数据执行唯一锚点检查及持久化。
6. Skills 与提示词提供领域流程和行为约束，不绕过业务校验，也不直接运行任意 Shell。

**当前 Runtime 验收目标：** 配置活动 Provider 后，SteamCMD、Minecraft 和写作各自的 AI Work 能创建、继续、归档会话并显示流式回复、Token 用量、Skill 注入、模型工具选择，以及按账户权限模式执行的逐项审批/自动工具调用和任务回传；未配置 Provider 或 Provider 不兼容工具调用时明确显示原因。当前模型请求与真实 Daemon 任务仍须在配置好凭据和在线节点的运行环境中完成验收。

### P7：多端与生产安装（进行中）

1. 当前根构建脚本的 Windows 默认桌面发布入口是 Tauri，Electron 保留维护入口；沿用既有路线，不在本轮切换外壳。远程主机部署控制端并由 Web 界面管理。
2. 安装包内携带匹配的 Node.js 运行时、控制端生产依赖、构建后的前端、Daemon 与 Windows Sandbox Host；包和中间产物只进入根 `dist/`。
3. 安装目录只保存程序；账户数据库、凭据、实例世界、Java 环境和备份留在 `%USERPROFILE%\\.LFAA\\data`，卸载和升级不得清理用户数据。
4. 用户可通过 localhost 同源使用 Web/API/Socket.IO。公网访问的内网穿透作为后续单独能力，需覆盖 Web、REST API 与 WebSocket，并沿用已有控制端鉴权；不在本轮安装包中捆绑隧道服务。
5. Linux 桌面外壳与 daemon 独立安装包待建设；Windows Tauri 安装、启动、升级/卸载数据保留和真实 Minecraft 主机验收仍需完成。

**验收目标：** Windows 新环境可安装 `LFAA 主版本.次版本.修订版本.exe`，无需预装 Node.js/pnpm 即可打开桌面端；本机账户和 Daemon 正常工作；卸载与升级保留 SQLite、凭据、游戏实例、世界存档、Java 环境和备份。远程 Web 部署不受本机桌面安装影响。

## 6. 进度维护规则

- 本文档是里程碑、进度和待办的唯一汇总处，不另外复制一份“开发进度”和“待开发清单”。
- 状态统一使用：`待开始`、`进行中`、`已完成`、`阻塞`。没有代码或可检查产物时，不标为已完成。

- 版本发布与正式版本变更仍记录在 `docs/updata-log.md`；普通任务状态变化只更新本文档。
- 每次开发开始前，先对照本文档、最新[系统总体架构](系统总体架构.md)和[开发规范](../开发规范.md)；用户最新确认的架构决策优先，旧文档只作背景参考。
